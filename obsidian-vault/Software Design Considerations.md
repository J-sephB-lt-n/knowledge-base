## General Design Principles

| Principle                                                                                                                                                                      | Motivation                                                                                                                                                                                           | How to Implement                                                                                                                                                                                 | Source                                                   |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| Modules should be decoupled                                                                                                                                                    | Decoupled code is easier to change                                                                                                                                                                   | Minimise shared dependencies between modules                                                                                                                                                     | Pragmatic Programmer 2nd ed.                             |
| Log messages should be structured                                                                                                                                              | This allows them to be efficiently filtered/search programmatically                                                                                                                                  | JSON logs in a chosen standard format                                                                                                                                                            |                                                          |
| Log messages should contain all of the 5 Ws: "Who, What, When, Where, Why"                                                                                                     | This gives sufficient context to work out precisely what actually happened and why                                                                                                                   |                                                                                                                                                                                                  |                                                          |
| Log messages should be correlated                                                                                                                                              | Gives visibility into the sequence of events leading to the failure                                                                                                                                  | - Add a globally unique shared ID to all logs corresponding to the same request/pipeline-run/experiment/user/etc.                                                                                |                                                          |
| No piece of information should have more than one source of truth                                                                                                              | Any piece of data/information/knowledge stored in more than 1 place WILL diverge.<br>This applies to data, config, documentation, everything                                                         |                                                                                                                                                                                                  | Joe                                                      |
| Modules should be deep with small interfaces                                                                                                                                   |                                                                                                                                                                                                      |                                                                                                                                                                                                  | A Philosophy of Software Design                          |
| Modules should be somewhat general                                                                                                                                             |                                                                                                                                                                                                      |                                                                                                                                                                                                  | A Philosophy of Software Design                          |
| Modules should be orthogonal                                                                                                                                                   | Eliminates effects between unrelated things.<br>If interfaces don't change, changing one module should not require changes to any other module.                                                      |                                                                                                                                                                                                  | Pragmatic Programmer 2nd ed.                             |
| Maximise concurrency/parallelism                                                                                                                                               |                                                                                                                                                                                                      | Look for opportunities to run lots of things at the same time                                                                                                                                    | Pragmatic Programmer 2nd ed.                             |
| Consider the efficiency of your code (time and resources) - estimate the order.                                                                                                |                                                                                                                                                                                                      | - Estimate objectively from measurements<br>- Don't prematurely optimise                                                                                                                         | Pragmatic Programmer 2nd ed.                             |
| A test is the first client of your API                                                                                                                                         | Writing a test first forces you to be the client.<br>Coupling and confusing interfaces are immediately apparent.<br>Forces design up front.<br>You get a useful test for free.                       |                                                                                                                                                                                                  | Pragmatic Programmer 2nd ed.<br><br>Domain-Driven Design |
| Do property-based testing                                                                                                                                                      | This makes you think about your code in terms of invariants and contracts                                                                                                                            |                                                                                                                                                                                                  | Pragmatic Programmer 2nd ed.                             |
| Think about security                                                                                                                                                           |                                                                                                                                                                                                      | - Minimise attack surface<br>- Principle of least privilege<br>- Use secure defaults<br>- Encrypt sensitive data<br>- Apply security patches quickly.<br>- Don't roll your own security code<br> | Pragmatic Programmer 2nd ed.                             |
| Don't live with broken windows                                                                                                                                                 | Letting quality slide (even a little) is a slippery slope.<br>New devs continue the patterns they see in a codebase.<br>If there isn't time to fix, at least board it up to show you are in control. |                                                                                                                                                                                                  | Pragmatic Programmer 2nd ed.                             |
| Design based on the domain (business problem) not the implementation technology                                                                                                | Domain experts can get closer to the software if the software structure matches their understanding of the domain system                                                                             |                                                                                                                                                                                                  | Domain-Driven Design                                     |
| Keep the domain layer isolated.<br>i.e. separate parts of the software dealing with domain logic from the non-domain parts (UI, I/O, networking, input validation, infra etc.) |                                                                                                                                                                                                      |                                                                                                                                                                                                  | Domain-Driven Design                                     |
| Technical domain experts (non-devs) must touch the code and devs must meet with domain experts and understand the domain model                                                 |                                                                                                                                                                                                      |                                                                                                                                                                                                  | Domain-Driven Design                                     |
| Decouple interface and implementation                                                                                                                                          | This allows other devs/teams to work against your interface before your implementation is completed                                                                                                  |                                                                                                                                                                                                  | Domain-Driven Design                                     |
| Think about the bigger picture (consider not only your immediate code but also everything affecting/affected by it)                                                            |                                                                                                                                                                                                      |                                                                                                                                                                                                  | Pragmatic Programmer 2nd ed.                             |
| Make quality a requirements issue<br>(tradeoffs in time, cost, reliability, performance, maintainability etc. are a user decision not a dev decision).                         | - Users know what they want better than you do.<br>- Many users would rather have rough software now than perfect software later.<br>                                                                |                                                                                                                                                                                                  | Pragmatic Programmer 2nd ed.                             |
